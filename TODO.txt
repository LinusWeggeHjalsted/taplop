Functional Prototype TODO
=========================

The goal is to load into a hub, walk into a mission, fight through a
level, and return to the hub — with visible output (native raylib now;
web via emscripten later).

Skill Logic
  Porting all implemented skills from the Unity project (~/Development/taplop
  Assets/Scripts/Skills). 26 total; slice + that_which_lingers already ported.
  Pattern: C# SkillScript -> Zig Skill struct + 5 fns (getValidTargets/priority/
  selectTarget/playerPrepareSkill/useSkill). Skills COMPOSE generic events
  (see AGENTS.md rule) — skill logic emits attack/heal/stun/etc.
  PORTING NOTE: Unity inverts AI priority (lower = higher priority, -1 = don't
  use); ziglop is higher = higher priority, 0 = don't use — FLIP the numbers
  when porting (see skill.zig priority_fn doc).
  Plan (agreed): primitives-first, then a skill-helper layer, then batches.
  [x] Primitives PR: new generic events heal / change_momentum /
      change_cooldown / swap_positions (+ attack.heals_attacker lifesteal hook,
      which emits a heal for the applied damage). Handlers clamp via
      functions.applySignedDelta (tested). Converted momentum already in
      getEffectiveOutgoingDamage; Impale/Skewer add one more getConvertedMomentum
      in-skill.
  [x] Skill-helper layer (src/skills/helpers.zig, excluded from the SkillId
      scan in build.zig): hostilesInRange / nearestTarget / highlightTargets /
      hostileEntityAt / ownedEvents. Each ported skill is now mostly its

Memory / Budget (decisions, revisit with real measurements)
  - Arenas are NOT fixed size: they grow from a backing allocator
    (ArenaAllocator -> DebugAllocator -> page_allocator -> OS/wasm). Allocation
    fails only when the backing fails: OS OOM (native, rare) or wasm memory.grow
    hitting the module maximum / 4 GiB wasm32 ceiling (the realistic case).
  - History keeps ~26 full GameState deep copies resident (16 snapshot slots +
    8 checkpoints + current + initial). Per-copy size ~= entities x ~4.2 KB
    (~90% is the inlined 96-slot inventory) + tiles x 8 bytes.
  - Decision: DON'T lazy-init enemy inventories. Inventory dominates Entity size
    but only matters at huge entity counts, which level caps prevent anyway;
    keep the simple inline array + uniform enemy pickup behavior.
  - Decision: level caps to bound worst case. max_entities = 256 for now
    (official levels ~16, but the level editor + level sharing will let players
    build massive levels). max_tiles ~10k as a starting estimate. Worst case
    ~= 26 x (max_entities x entity_size + max_tiles x 8) ~= tens of MB.
  - Decision: estimate caps now, tune with measurement later. Add peak-usage
    reporting via DebugAllocator once the renderer + a real level exist, then
    set the true wasm budget + caps from real numbers.
  - Decision: leave memory growable but set a generous safety ceiling
    (~256-512 MB) so runaway bugs (infinite event push, bad deep copy) fail
    fast at a @panic instead of killing the tab. Not a tight fit — real
    non-asset usage is single-digit MB for normal levels.
  - event_history grows unbounded (every event, tens of bytes each) to power
    infinite undo. Accepted: growth is tiny, feature is worth it, extreme
    sessions would fail-fast rather than corrupt.

Asset Memory (decisions, from Unity project audit ~/Development/taplop)
  - Disk size is NOT memory size. Current assets: 122 PNGs = 4.1 MB on disk but
    ~325 MB decoded RGBA (~433 MB w/ mipmaps); 16 WAVs = 34.8 MB (one 33.5 MB
    Ambient music track, all SFX ~1.3 MB combined).
  - Textures are the dominant consumer (~80x the PNG folder once decoded), not
    gamestate. PNG compression is irrelevant to VRAM: GPU needs raw RGBA =
    w*h*4. Source art is oversized (Flag 4096x1024 = 16 MB; every weapon
    2048x1280 = 10 MB) for a grid game rendering at ~256px.
  - Two separate budgets: wasm linear heap (gamestate/events/decoded SFX/temp,
    small) vs GPU/texture memory (browser-managed on WebGL, large, art-driven,
    off the wasm heap). Streamed music also stays off the wasm heap; fully
    decoded audio lands on it.
  - In-memory lossless compression is NOT the lever. Levers, in impact order:
    1. Downscale source sprites to display resolution (~325 MB -> <50 MB, no
       perceptible loss). Biggest memory + web-download win. NOTE: confirm
       whether sprites are animation sheets first — affects how far we can shrink.
    2. Stream music as OGG (raylib LoadMusicStream): ~33 MB -> tiny ring buffer
       + decoder; disk ~33 MB -> ~3-4 MB.
    3. SFX: fully decode to PCM (memory trivial); OGG only helps download size.
    4. GPU texture compression (ASTC/ETC2/BC via KTX2/Basis) only if later
       measurements demand it — lossy, WebGL/raylib support fiddly.
  - Web download budget: PNG (lossless) for art + OGG for audio takes asset
    download from ~39 MB to ~8 MB, mostly art.

Content Loading / Custom Missions (direction, build with platform layer)
  - Core principle: SEPARATE acquiring a mission from reading it. Acquisition
    (upload dialog / directory scan / online fetch) is one-time, possibly
    interactive or async. Reading mission files during gameplay AND replay must
    be synchronous, silent, repeatable.
  - Route ALL content reads through a resident "mission/asset source"
    abstraction: readFile(logical_path) -> bytes, from memory or disk. Impls:
      * built-in / native disk: Dir-backed (today's history.directory/io)
      * zip upload (browser dialog): extract to in-memory VFS (path->bytes)
      * custom directory: Dir-backed at a chosen path
      * online database: fetch by immutable id/url -> cache into in-memory VFS
  - parseConfigFileFromPath + asset loads go through the source instead of
    std.Io.Dir directly.
  - Source lives on GameStateHistory (like directory/io/settings), NOT in the
    replayed GameState — session-resident, available for every replay re-read,
    never deep-copied into snapshots.
  - Replay-safety falls out for free: dialog/fetch happens in an acquisition
    step (idle input), never in an event handler. The recorded event is
    start_mission referencing an already-resident source, so replay re-reads
    silently and never re-fires the dialog (same pattern as load_save's picker).
  - Under route B (emscripten + raylib), web content loads through raylib's
    LoadFileData against emscripten's virtual FS (assets packaged at build
    time), so the freestanding "no filesystem" constraint below no longer
    dictates the design. The mission/asset-source abstraction is still worth it
    for custom missions (upload/fetch), just not forced by the web target.
  - (Historical, freestanding route A — abandoned) freestanding WASM has no cwd
    filesystem, so even built-in content needs a non-Dir source on web.
  - Caching: acquire once, cache raw bytes; future reads (replay re-loads,
    retry, renderer asset loads) hit the cache. Real win is avoiding expensive
    re-acquisition (network re-fetch / zip re-decompress), not re-parse. Cache
    is session-scoped — a fresh session re-acquires unless persisted.
  - Async wrinkle: online fetch / zip read is async on web. Acquisition must
    fully populate the source ("loading mission...") before emitting
    start_mission.
  - Cross-session replay reproducibility: a shared/saved replay of a custom
    mission is only reproducible with the exact mission bytes. Mission refs
    should eventually be content-addressed (hash) or pinned to an immutable
    version id — matters for recorded-history-as-test and replay sharing.

      unbounded, backs event_history + idle_points and holds deep-copied event
      payloads (event slices are the replay source of truth, must outlive
      current_arena resets); (b) current_arena — owns live current_state, and is
